# Generated Post Feedback and Preference Guidance Design

## Summary

Add an opt-in Generated Post Feedback system that lets administrators Like, Dislike, change, or clear feedback on every post generated by AI Post Scheduler. Optional reason categories and comments turn those reactions into bounded, context-sensitive prompt guidance for future generation.

The system generalizes the useful ideas behind `AIPS_Topic_Penalty_Service` and `AIPS_Topic_Expansion_Service`: weighted positive and negative signals, semantic similarity, scoped context, and configurable influence. It does not make those topic-specific classes responsible for posts. New post-feedback components use the shared `AIPS_Generator` and prompt-builder path so feedback can inform every generation flow rather than only Author Topic posts.

The feature is disabled by default for both new installations and upgrades. A global master switch is authoritative: when it is off, neither Author nor Template configuration can enable the feature, and generation performs no feedback queries, retrieval, embedding, or prompt augmentation.

## Goals

- Collect an administrator's current Like or Dislike reaction for any generated post.
- Allow an optional structured reason and free-text editorial comment.
- Preserve an append-only audit history when feedback changes or is cleared.
- Apply feedback to all post-generation paths that use `AIPS_Generation_Context` and `AIPS_Generator`.
- Support global defaults plus per-Author and per-Template enablement and weight overrides.
- Enforce precedence centrally: global master switch, then Template overrides, then Author overrides, then global defaults.
- Retrieve semantically relevant feedback rather than injecting indiscriminate global examples.
- Route feedback guidance to content, title, excerpt, and SEO metadata according to its reason.
- Bound prompt size, preserve explainability, and fail open when feedback infrastructure is unavailable.
- Keep Topic Feedback and Post Feedback as separate domains.

## Non-goals

- Fine-tuning or training an external model.
- Automatically publishing, approving, rejecting, or deleting a post based on feedback.
- Automatically changing an Author Topic's score when a generated post is liked or disliked.
- Treating a Like as editorial approval or a Dislike as rejection.
- Requiring a reason or comment.
- Backfilling embeddings for every existing generated post during upgrade.

## Terminology

- **Feedback event:** An append-only record with a reaction of `liked`, `disliked`, or `cleared`.
- **Current feedback:** The latest feedback event for a post.
- **Effective policy:** The fully resolved enabled state, weights, limits, and thresholds for one generation context.
- **Feedback guidance:** The bounded prompt material created from relevant current feedback.
- **Content-integrity factor:** A ranking multiplier derived from whether the post content still matches the hash captured when feedback was submitted.
- **Scope:** Global, Author, or Template applicability of feedback and configuration.

## Existing Architecture and Extension Points

All major generation flows converge on `AIPS_Generator::generate_post()`, which converts legacy calls to `AIPS_Template_Context` and delegates to `generate_post_from_context()`. Author Topic generation passes an `AIPS_Topic_Context`. The content prompt is built through `AIPS_Prompt_Builder_Post_Content`, and contextual instructions are built through the shared `AIPS_Prompt_Builder`.

The implementation will resolve and retrieve feedback once near the start of `generate_post_from_context()`. The resulting immutable prompt context will be passed to specialized prompt builders. This avoids adding feedback behavior separately to schedulers, campaigns, planner jobs, manual generation, Author Topics, trending topics, bulk jobs, or regeneration controllers.

The current topic services remain unchanged in responsibility:

- `AIPS_Topic_Penalty_Service` adjusts Author Topic scores and policy flags.
- `AIPS_Topic_Expansion_Service` finds semantically similar approved Author Topics.
- New Post Feedback services store reactions, resolve configuration, retrieve similar rated posts, and assemble post-generation guidance.

The existing `AIPS_Embeddings_Service` provides vector generation, similarity calculation, and nearest-neighbor behavior. The existing post-embedding infrastructure should be reused or safely extended instead of introducing another embedding provider.

## Configuration Model

### Global settings

Register all defaults in `AIPS_Config::get_default_options()` and expose them in a new Generated Post Feedback section on Settings.

Initial global settings:

| Setting | Default | Meaning |
|---|---:|---|
| Master enabled | Off | Absolute core switch |
| Like influence | 1.0 | Positive-signal multiplier |
| Dislike influence | 1.25 | Negative-signal multiplier |
| Semantic similarity weight | 1.0 | Importance of topical relevance |
| Recency weight | 0.35 | Strength of time decay |
| Author-match weight | 1.25 | Boost for matching AIPS Author |
| Template-match weight | 1.5 | Boost for matching Template |
| Global-pool weight | 0.5 | Cross-scope influence |
| Maximum examples | 6 | Candidate prompt inclusion cap |
| Minimum similarity | 0.70 | Retrieval eligibility threshold |
| Minimum feedback sample count | 1 | Minimum usable current reactions |
| Prompt budget | 4,000 characters | Maximum serialized guidance size before final prompt assembly |

The final option keys and numeric bounds must follow existing `aips_` naming and Settings sanitization patterns. Invalid values fall back to registered defaults; numeric values are clamped to documented ranges.

### Author and Template settings

Add dedicated nullable `feedback_enabled` fields and nullable/empty `feedback_config` JSON fields to `aips_authors` and `aips_templates`.

- `feedback_enabled = NULL`: inherit.
- `feedback_enabled = 1`: enable when the global master switch is on.
- `feedback_enabled = 0`: disable for this scope.
- `feedback_config`: a sparse map containing only explicit weight, limit, or threshold overrides.

Do not store this configuration in an Author's free-form `details` field or a Template prompt. Repositories and DTOs must expose typed accessors or properties, and controllers must sanitize allowed keys only.

### Resolution precedence

`AIPS_Post_Feedback_Config_Resolver` is the only component that interprets hierarchy.

1. Read global master switch. If off, return an immutable disabled policy immediately.
2. Start with global weights and limits.
3. Apply Author enabled state and sparse overrides when an AIPS Author is present.
4. Apply Template enabled state and sparse overrides when a Template is present.
5. Return the effective policy.

Template values override Author values when both scopes exist. Author values override global defaults. No lower-level scope can bypass a disabled global master switch.

Although current `AIPS_Template_Context` and `AIPS_Topic_Context` flows are normally distinct, the resolver must support a future context that exposes both Template and Author identifiers.

## Data Model

### `aips_post_feedback`

Create an append-only table with at least:

| Column | Purpose |
|---|---|
| `id` | Monotonic primary key |
| `post_id` | WordPress post receiving feedback |
| `history_id` | Generation history row, when available |
| `user_id` | Administrator who submitted the event |
| `reaction` | `liked`, `disliked`, or `cleared` |
| `reason_category` | Optional normalized category |
| `comment` | Optional sanitized editorial comment |
| `content_hash` | Hash of normalized title/content/excerpt at feedback time |
| `author_id` | AIPS Author scope snapshot, nullable |
| `template_id` | Template scope snapshot, nullable |
| `created_at` | `AIPS_DateTime`-compatible timestamp |

Indexes must support latest-event lookup by post, retrieval by reaction, Author, Template, history, and time. The latest event by monotonically increasing ID determines current state. A `cleared` latest event means the post has no current feedback but retains its audit history.

Do not update or delete prior events during normal UI operations. A separate explicit data-management action may delete feedback in accordance with plugin data-retention controls.

### Content and embeddings

On Like or Dislike:

1. Verify the post is marked `_aips_generated_post = '1'`.
2. Capture the current normalized content hash.
3. Record generation origin from history/post metadata.
4. Ensure an embedding exists for the rated version, synchronously only when cheap and otherwise through the existing background indexing mechanism.

The embedding input should be a bounded combination of title, excerpt, topic, and representative post content. It must not include the administrator's comment as part of the post semantic vector.

No upgrade-time bulk embedding backfill is required. Existing posts enter the feedback pool when they first receive Like or Dislike feedback.

## Feedback Reasons

Use one normalized taxonomy with reaction-aware labels:

- `tone_style`
- `originality`
- `relevance`
- `accuracy`
- `structure`
- `depth`
- `engagement`
- `seo`
- `policy_safety`
- `other`

The reason and comment are optional. UI labels should read positively for Likes and negatively for Dislikes, while storage uses the same stable category keys.

Reason-specific configurable multipliers may be added to the global and sparse override maps. Unspecified reasons use a neutral multiplier of `1.0`.

## Services and Responsibilities

### `AIPS_Post_Feedback_Repository`

- Append feedback events.
- Get current feedback for one or many posts without N+1 queries.
- Get audit history for a post.
- Query current liked/disliked candidates by applicable scope and time.
- Exclude a latest `cleared` event from the active candidate pool.
- Keep SQL and persistence out of controllers and prompt services.

### `AIPS_Post_Feedback_Service`

- Validate reaction transitions and supported reasons.
- Verify generated-post eligibility.
- Capture origin metadata and content hash.
- Record Like, Dislike, or Clear operations.
- Schedule or request embedding creation.
- Return current-state and audit data suitable for UI responses.

### `AIPS_Post_Feedback_Config_Resolver`

- Resolve the authoritative effective policy.
- Normalize and clamp values defensively.
- Short-circuit all downstream work when globally or effectively disabled.

### `AIPS_Post_Feedback_Retrieval_Service`

- Build a semantic query from the pending generation context.
- Retrieve a bounded candidate set of posts whose latest event is liked or disliked.
- Apply similarity threshold, scope eligibility, content availability, content integrity, and configured weights.
- Return separate ranked positive and negative candidates plus diagnostic metadata.
- Queue missing embeddings and fail open rather than blocking generation.

### `AIPS_Post_Feedback_Prompt_Context`

- Transform ranked candidates into immutable, reason-aware guidance.
- Produce component-specific guidance for content, title, excerpt, and SEO metadata.
- Enforce maximum examples and prompt budget.
- Include short positive excerpts only when useful.
- Represent negative feedback as distilled avoidance guidance, never as full disliked content.
- Treat comments as untrusted editorial observations rather than executable instructions.
- Expose selected feedback IDs and size metrics for history logging.

## Retrieval and Ranking

Maintain separate positive and negative pools so one reaction type cannot crowd out the other. Candidate eligibility requires:

- Latest reaction is `liked` or `disliked`.
- Source post still exists and has usable content for positive examples.
- Similarity meets the effective minimum threshold.
- Candidate belongs to an allowed applicable scope.
- The effective policy has enough active feedback samples.

Conceptual ranking:

```
score = similarity_component
      * scope_multiplier
      * reaction_multiplier
      * reason_multiplier
      * recency_multiplier
      * content_integrity_multiplier
```

The exact formula must be deterministic, documented in code, and covered by focused unit tests. Weight `0` must cleanly disable the corresponding influence rather than creating division-by-zero or negative-ranking behavior.

Scope behavior:

- Matching Template candidates receive the Template-match boost.
- Matching Author candidates receive the Author-match boost.
- Other eligible rated posts use the global-pool multiplier.
- When both Template and Author match, Template precedence governs configuration, while the ranking implementation may apply the more specific scope boost rather than multiplying both without bound.

Recency uses a bounded decay so older feedback remains usable but contributes less. The content-integrity factor is `1.0` when the current hash matches the feedback snapshot and a configurable lower value after material edits. Trashed or deleted posts retain audit events but are excluded from example content.

## Prompt Construction

Resolve feedback once per generation and attach the resulting context to the shared generation pipeline. Do not independently re-query feedback in each specialized builder.

The guidance block has two sections:

- **Prefer:** Distilled traits from liked posts and optional short positive excerpts.
- **Avoid:** Distilled problems from disliked posts and their reasons.

Component routing:

| Reason | Content | Title | Excerpt | SEO metadata |
|---|:---:|:---:|:---:|:---:|
| Tone/style | Yes | Limited | Limited | No |
| Originality | Yes | Yes | Limited | No |
| Relevance | Yes | Yes | Yes | Yes |
| Accuracy | Yes | No | Limited | Limited |
| Structure | Yes | No | Limited | No |
| Depth | Yes | No | Limited | No |
| Engagement | Yes | Yes | Yes | Limited |
| SEO | Limited | Yes | Yes | Yes |
| Policy/safety | Yes | Yes | Yes | Yes |
| Other | Yes | Limited | Limited | Limited |

“Limited” means a concise derived instruction, not full example material. Featured-image prompts are not affected in the initial release because the feedback taxonomy describes the generated post as a whole and has no image-specific signal.

Existing Author Topic expanded context and new feedback guidance remain separately labeled and separately budgeted. If the total prompt budget is constrained, preserve explicit Template/Author instructions and safety constraints first, then feedback guidance, then optional examples.

Record the effective enabled state, scope, candidate counts, selected feedback event IDs, component routing, final guidance size, and fallback reason in generation history. Do not duplicate full rated-post content or sensitive comments in logs.

## Prompt Injection and Data Safety

Administrator comments are still untrusted prompt data. The prompt-context builder must:

- Normalize and length-limit comments.
- Strip markup and control characters.
- Delimit comments as quoted editorial observations.
- State that observations must not override system, safety, Template, Author, or site instructions.
- Ignore or neutralize instruction-like phrases where practical.
- Never use comments as system messages or provider options.

Only users with `manage_options` may submit or clear feedback. Every mutation requires a nonce, sanitized input, an allowed reason/reaction, and a verified generated-post marker.

## Generated Posts UI

Add to every generated-post row:

- Like and Dislike buttons with selected state.
- Optional reason and comment panel after reaction selection.
- Clear Feedback action.
- Accessible labels, pressed states, keyboard behavior, and localized notices.
- Filters for Liked, Disliked, and No Feedback.
- Bulk Like, Dislike, and Clear actions with optional shared reason/comment.

The current Generated Posts query is draft-oriented. Feedback controls and filters must operate on all posts carrying the generated-post marker, including draft, published, private, pending, and trashed items where the page intentionally exposes them. Existing review-only behavior must not silently prevent feedback on other generated statuses.

Register all AJAX actions in `AIPS_Ajax_Registry`. The controller owns capability and nonce checks, sanitization, eligibility validation, and `AIPS_Ajax_Response` output.

## WordPress Post Editor UI

Add a Generated Post Feedback panel or meta box when `_aips_generated_post = '1'`:

- Same Like, Dislike, reason, comment, and Clear behavior as the Generated Posts page.
- Current reaction is loaded from the repository.
- The panel remains available after publish or manual edits.
- Saving the WordPress post does not implicitly submit or change feedback.

Reuse a shared UI partial and JavaScript behavior where practical so the two surfaces do not drift.

## Regeneration and Version Lineage

Regeneration creates a new unrated post. It must not copy the old post's current reaction to the new content. The old feedback remains attached to the old version and may inform regeneration according to the effective policy.

Store predecessor lineage on the new post as `_aips_predecessor_post_id` and in generation-history metadata before deleting or trashing the replaced post. The new post begins with no current feedback. This preserves an honest learning loop: the administrator must rate the new output independently.

If existing regeneration permanently deletes the predecessor, retain its feedback audit row and enough bounded snapshot/origin metadata to explain the signal, but do not retain full post content solely for this feature unless existing WordPress retention already does so.

## Disabled and Failure Behavior

The feature is fail-open for generation:

- Global master off: return disabled before repository or embedding work.
- Effective Author/Template policy off: generate normally.
- Too few feedback samples: generate normally.
- Missing query or candidate embeddings: queue indexing and continue.
- Embedding provider unavailable: generate normally and record a concise fallback.
- Repository/query failure: log through existing logging/history services and generate normally.
- Oversized guidance: rank and truncate deterministically.
- Missing/deleted source content: exclude example content while retaining the audit event.
- Invalid configuration: clamp or fall back to registered defaults.

Feedback failure must never make a post generation fail, downgrade its status, or mark a component incomplete.

## Migration and Lifecycle

- Add the table and Author/Template columns to fresh-install schema in `AIPS_DB_Manager`.
- Add an idempotent versioned migration in `AIPS_DB_Migrations` for existing installations.
- Update schema catalogs, datetime maps, repository boundary checks, DTOs, and repair/reinstall behavior.
- Register defaults for both new installations and upgrades; master enabled remains false.
- Do not perform bulk embedding backfill during migration.
- Ensure uninstall/data-management behavior explicitly includes or preserves post feedback according to the plugin's existing data-retention choice.

## Testing Strategy

### Configuration

- Global off always wins over Author and Template settings.
- Template overrides Author; Author overrides global defaults.
- Sparse override maps inherit unspecified values.
- Invalid values are rejected, normalized, or clamped.
- Disabled policies perform no feedback repository or embedding work.

### Persistence and service behavior

- Like, Dislike, Clear, and reaction changes append events.
- Latest event determines current state.
- Clearing removes a post from the active pool without deleting audit history.
- Bulk current-state lookup avoids N+1 queries.
- Origin metadata and content hashes are captured correctly.
- Only generated posts and authorized administrators are accepted.

### Retrieval and prompts

- Positive and negative pools rank independently.
- Similarity, scope, reaction, reason, recency, and integrity weights affect deterministic ordering.
- Minimum sample, similarity, example, and prompt-budget limits are enforced.
- Comments cannot escape their editorial-observation boundary.
- Disliked full content is never inserted into prompts.
- Reason guidance routes only to intended components.
- Selected event IDs and guidance metrics are recorded without full sensitive content.
- Topic-expanded context and feedback guidance coexist within separate budgets.

### Generation coverage

- Template, scheduled, manual, campaign, planner, trending, bulk, Author Topic, and regeneration paths that use `AIPS_Generator` receive the same resolver behavior.
- Legacy generator calls converted to `AIPS_Template_Context` are covered.
- Feedback outages do not fail generation or mark it partial.
- Whole-post feedback influences content, title, excerpt, and SEO metadata as routed.

### UI and security

- Generated Posts row actions, filters, bulk actions, notices, and accessibility states.
- Post-editor feedback panel on generated posts only.
- Nonces, `manage_options`, generated marker, reason allowlist, and input length limits.
- Published, manually edited, trashed, and deleted post behavior.
- Regenerated posts start unrated and retain predecessor lineage.

### Schema

- Fresh-install schema matches upgraded schema.
- Migration is idempotent.
- Repair/reinstall operations include new structures.
- Datetime handling uses `AIPS_DateTime` conventions.

Per repository policy, implementation verification should use focused static and syntax checks by default. Focused PHPUnit tests should be run when implementation requires them or when explicitly approved.

## Observability

Generation history should capture:

- Whether the feature was globally and effectively enabled.
- Resolved Author and Template scope identifiers.
- Candidate and selected counts by reaction.
- Selected feedback event IDs.
- Effective thresholds and bounded guidance size.
- Missing-embedding, insufficient-sample, truncation, or repository fallback reason.

Do not log full source posts or free-text comments. Use existing `AIPS_History_Service`, `AIPS_History_Container`, `AIPS_Logger`, and correlation IDs.

## Rollout

1. Ship schema, configuration resolver, repository, and service behind the disabled master switch.
2. Add feedback mutation/read APIs and both admin UI surfaces.
3. Add asynchronous indexing for rated posts.
4. Integrate retrieval and bounded guidance into the shared generator and prompt builders.
5. Add observability and focused coverage for every context type.
6. Document settings, inheritance, weights, privacy, and failure behavior.

The feature remains opt-in on new and upgraded installations. Enabling it begins learning only from feedback recorded by administrators; unrated historical posts do not influence prompts.

## Acceptance Criteria

- An administrator can Like, Dislike, change, or clear feedback for any generated post from both the Generated Posts page and WordPress editor.
- Reasons and comments are optional; all changes remain auditable.
- Global off prevents all overrides and all runtime feedback work.
- Effective settings follow Template, Author, global precedence and expose configurable weights.
- Feedback can influence every shared generation path, not only Author Topics.
- Similar feedback is retrieved semantically and constrained by scope, ranking, and prompt budgets.
- Disliked full content is never copied into prompts.
- All textual components receive reason-appropriate guidance; featured-image generation is unchanged initially.
- Failures in feedback storage, retrieval, or embeddings do not fail post generation.
- Regenerated posts begin unrated and link to their predecessors.
- The feature is disabled by default and requires explicit administrator opt-in.
